## 代码与改动

- 保持小步变更，只处理本次任务；不顺手重构无关代码，不覆盖或丢弃用户已有修改。重叠改动先核对。
- 优先复用现有模块和接口，保持高内聚、低耦合，遵守分层和依赖方向；避免超大函数、过深嵌套和重复实现。
- 沿用项目已有编码风格，标识符使用英文。注释语言跟随项目已有代码风格；所属模块有明确约定时沿用该约定，没有既有风格或约定时默认使用英文。
- 代码关键位置必须添加详细注释，说明原理、目的、边界条件、使用限制及容易踩坑的原因，帮助后续维护者避免再次踩坑；注释应解释代码背后的依据，避免只重复代码表面含义。
- BUG 修复在相关代码附近补充触发条件、根因和修复依据；曾经踩过的坑应写明不能采用的做法及原因，并在代码变更时同步维护注释。
- 配置、错误处理和资源释放要完整；缺失的外部能力明确报告不可用，不伪造数据或成功状态。
- 不提交本轮临时工具、无关生成物、个人配置、账号、密钥或其他敏感信息。需要保留的维护工具应明确归档。
- 源码和共享脚本不写死本机绝对路径、用户名、地址或凭据；环境差异通过配置、参数或环境变量传入。

## 验证与交付

- 根据影响范围完成必要的静态检查、构建、测试或实际运行；纯文档修改检查内容、路径和引用。

## Git 与发布

- Git 操作前确认真实仓库、分支和已有改动；只纳入本次任务文件，不使用破坏性命令清理现有工作区。
- 验证通过后，普通单仓项目可主动本地提交；多仓、只读仓、游离 HEAD 或有特殊分支要求时，先核对对应约定及授权。
- 推送、Tag、Release 和部署按用户明确授权执行，沿用会话中已获得的授权；本地提交、打包不等于发布。
- 提交信息、共同作者行及交付材料不添加 AI 署名或 AI 辅助编程声明；提交前核对 Git 身份，推送前核对远程仓库和目标分支。
- 改写已推送历史、移动已发布 Tag 或强制推送，须有针对该操作的明确授权。
